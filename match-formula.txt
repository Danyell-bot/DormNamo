DORMNAMO - HOW THE MATCH % IS CALCULATED
=========================================

Code: js/app/state.js (weights), js/matching/matching.js (facts, ev, score, queue),
      js/matching/twotower.js (learning model).

The match % blends two parts:
  (A) a weighted checklist of the student's stated preferences, and
  (B) a small learning model (Two-Tower) that counts more the more the student swipes.


1. PREFERENCES AND WEIGHTS
--------------------------

Each preference has a strictness the student sets (S.P.m[k]):
  0 = don't care      (ignored)
  1 = nice to have    (affects the ranking)
  2 = must have       (hard filter)

Each preference has a fixed ranking weight (W in state.js):

  Preference                 Key      Weight w
  -------------------------  -------  --------
  Walking distance           dist        9
  Budget                     budget      8
  Room capacity              cap         7
  Gender accommodation       gender      7
  Reliable 24/7 water        water       6
  Electricity in rent        elec        5
  Clean, peaceful, safe      env         4
  Kitchen / cooking area     kit         3
  Wi-Fi / internet           wifi        3
  Spacious room              space       2
  No curfew                  curfew      1
  Visitors allowed           vis         1

Default preferences (DEF): school MSU-IIT, max 1.5 km, boarding house budget P6,000,
apartment budget P9,000, capacity "2-3", gender "any". Distance is a must-have (2),
everything else nice to have (1).
Capacity and gender are only checked when they are not "any".
Apartments are checked against the apartment budget (aptMax), others against bhMax.


2. CHECKING EACH PREFERENCE AGAINST A ROOM - ev(h)
-------------------------------------------------

Every active preference gets one of three results:
  true   the listing confirms it
  false  the listing contradicts it (e.g. rent is over budget)
  null   unknown (the listing doesn't say)

Where the facts come from:
  1. The owner's stated facts (h.facts) always win.
  2. Otherwise facts(h) reads the listing name, description, amenities and reviews
     with keyword rules, e.g. "wi-fi" -> Wi-Fi = true, "kitchen" -> kitchen = true,
     "clean / safe / quiet" -> env = true, "curfew" -> has a curfew.
  Unknown values are never guessed.


3. CHECKLIST SCORE - score(h)
-----------------------------

Over the active preferences (strictness >= 1):

  T = sum of w over ALL active preferences           (everything you care about)
  K = sum of w over preferences that are KNOWN       (true or false)
  E = sum of w over preferences that are TRUE        (confirmed matches)

  pct      = E / K               share of known facts that match   (0 if K = 0)
  coverage = K / T               how much of the room is actually known
  rule     = pct x (0.7 + 0.3 x coverage)

Why coverage: a room with only one known fact can't score 100%.
A perfect match on few facts is capped near 70%; only a fully known room reaches 100%.


4. LEARNING MODEL - Two-Tower (twotower.js)
-------------------------------------------

Room vector dvec(h), 15 numbers (each 0..1):
  rent / 9000, distance / 5 km, capacity / 6, capacity known, Wi-Fi, kitchen, water,
  aircon, CCTV, curfew, allows male, allows female, mixed, verified, rating / 5

Student vector uvec(), 44 numbers:
  budget / 9000, max km / 5, capacity (4 -> 0.67, 2-3 -> 0.5, any -> 0),
  gender male / female / mixed,
  strictness / 2 for wifi, kit, water, elec, env, space, curfew, vis,
  + the average room vector of liked and bookmarked rooms (15),
  + the average room vector of passed rooms (15)

Each side goes through its own small network (12 outputs, tanh):
  u' = tanh(Wu x uvec)      d' = tanh(Wd x dvec)
  cos = cosine(u', d')      between -1 and 1

Training: after each action, 3 passes of gradient descent (learning rate 0.05) over the
last 60 actions, loss on sigmoid(5 x cos) vs the label y, scaled by the weight w:

  Action                           Label y   Weight w
  -------------------------------  -------   --------
  Like / heart                        1         1
  Pass                                0         1
  Bookmark                            1         1.5
  Asking Namo about a room            1         0.3

The starting weights are fixed (seeded random, lcg(7)), so everyone starts the same.


5. FINAL MATCH %
----------------

  alpha = min(0.5, (likes + passes + bookmarks) / 40)    trust in learning grows with use
  final = (1 - alpha) x rule  +  alpha x (cos + 1) / 2
  Match % = round(final x 100)

  - 0 swipes: alpha = 0, the % is purely the stated preferences.
  - 20+ swipes: alpha = 0.5, stated preferences and behavior count equally.

Must-haves (strictness 2):
  - a must-have that is FALSE removes the room from the matches (queue()).
  - a must-have that is UNKNOWN keeps the room but lowers its sort order:
      sort key = final - 0.05 x (number of unknown must-haves)
    The % shown does not change.

Rooms in Discover / "best for me" are sorted by that sort key, highest first.
Rooms already liked, passed or bookmarked are left out of the Discover deck.


6. WORKED EXAMPLE - Uy Pad Residences, default preferences
----------------------------------------------------------

  Preference                               w    Result
  ---------------------------------------  ---  -------------
  Distance (0.6 km <= 1.5 km, must-have)   9    TRUE
  Budget (rent not published)              8    unknown
  Capacity (2-3 people)                    7    unknown
  Water                                    6    unknown
  Electricity                              5    unknown
  Clean / peaceful (said in reviews)       4    TRUE
  Kitchen                                  3    unknown
  Wi-Fi                                    3    unknown
  Spacious                                 2    unknown
  Curfew                                   1    unknown
  Visitors                                 1    unknown
  (Gender is "any", so it isn't counted.)

  T = 9+8+7+6+5+4+3+3+2+1+1 = 49
  K = 9 + 4 = 13
  E = 13

  pct      = 13 / 13 = 1.00
  coverage = 13 / 49 = 0.265
  rule     = 1.00 x (0.7 + 0.3 x 0.265) = 0.780   ->  78%

With learning, e.g. after 10 swipes (alpha = 0.25) and a model cosine of 0.4:

  final = 0.75 x 0.780 + 0.25 x (0.4 + 1) / 2
        = 0.585 + 0.175
        = 0.760                                    ->  76%


NOTES
-----
- The % is a ranking score, not a probability that the student will like the room.
- Unknown details never count as matches; they only lower coverage. That is why most
  current listings (rent and rules not published online) sit around the 70s.
- To change the priorities, edit W in js/app/state.js. To change how quickly learning
  takes over, edit alpha() in js/matching/matching.js (the 40 and the 0.5 cap).
