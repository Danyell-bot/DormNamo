# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Running

Static site, no build step, no linter. Open `index.html` (Rooms), `discover.html` (swipe feed), `mylistings.html` (owners edit their listings), `people.html` (accounts: landowners and students) or `messages.html` (chats) in a browser. Deploy by uploading the folder to GitHub Pages. `package.json` exists only for tooling, not for the site. The tools need Node ≥ 21.7 (they use `process.loadEnvFile`):

- `npm test`: Node's built-in test runner (`node --test tests/`), no dependencies. Run one file with `node --test tests/worker.test.mjs`, or one test with `node --test --test-name-pattern="cache expires" tests/`.
- `npm run config`: writes the gitignored `js/app/config.js` (browser key, Map ID, worker URL) from `.env`.
- `npm run nearby [-- --all]`: saves OpenStreetMap nearby places for pinned dorms into `js/data/nearby-snapshot.js` (no key).
- `npm run geocode [-- --dry-run|--force|--max-age-days N]`: saves `lat`/`lng` into `js/data/data.js` (needs `GOOGLE_MAPS_SERVER_KEY`).
- `npm run worker:dev` / `npm run worker:deploy`: the Cloudflare Worker through `npx wrangler`.

Never put a real key in source. Keys live in `.env` (gitignored); `.env.example` documents them.

## Architecture

**Layout:** browser code is grouped by purpose in `js/{app,account,data,listings,matching,maps,namo,pages}/` and styles in `css/{base,components,pages}/`; every folder (`js`, `css`, `tools`, `worker`, `tests`) has a `README.md` with a one-line purpose per file. File names below are given without their folder. Node tools and tests find browser scripts through `tools/js-files.mjs` (`jsPath("data")` → `js/data/data.js`), so moving a file means updating that map, the `<script>`/`<link>` tags in all four pages, and the folder README.

Plain ES5-style browser JS. There are no modules: every file defines globals (`HOUSES`, `S`, `USER`, `$`, `esc`, `score`, `draw`, …) or an IIFE namespace (`Accounts`, `Auth`, `Onboarding`, `Nav`, `FX`, `Chat`, `Argon2id`). **Script order in each HTML file is the dependency graph.** If you add a file or a global, add the `<script>` tag to `index.html`, `discover.html`, `mylistings.html`, `people.html` and `messages.html` in the right place. Page-only scripts: `browse.js`, `owners.js` and `hero-fx.js` load only on `index.html`, `discover.js` only on `discover.html`, `mylistings.js` only on `mylistings.html`, `people.js` only on `people.html`, `messages.js` only on `messages.html`, and `select.js` on Rooms and My listings, so shared code must guard them (`if (window.HeroFX) …`). `pin.html` has its own short list (`data`, `utils`, `pins`, `nearby-core`, `maps`, `pin-tool`). `js/app/config.js` is gitignored but loaded by every page; `js/app/config.example.js` is the template, and the code must work when it is missing or empty. Both pages also need the same overlay/dialog elements (`#auth`, `#ob`, `#toast`, `#dlg`).

**Consent first (`js/app/consent.js`, right after `utils.js` on the three app pages):** `boot()` first calls `Consent.show(boot)` until the student has chosen. "Accept preference cookies" → `Accounts.saveState` writes `localStorage` and `save()` also writes the `dn_prefs` cookie (school, walk, budget, must-haves; 180 days, `Path` = this site's folder, `SameSite=Lax`, `Secure` on https), which `browse.js` reads on load to start the Rooms search from them. "Essential only" → state lives only in `sessionStorage` for this tab and `Accounts.forgetStates()` deletes saved states and the cookie. Always kept: accounts, the session and the choice (`dn_consent` cookie, mirrored in `localStorage` because `file://` ignores cookies). Changeable from the account menu ("Privacy & cookies"). GitHub Pages never reads cookies server-side; only the site's JS does. Insights (learning) and Gemini keep their own separate consent. Tests: `tests/consent.test.mjs`.

**Start-up (`main.js`):** `boot()` → `Accounts.current()`. With no session it calls `Auth.show(boot)`. With a session it runs `loadState(user)`, then shows `Onboarding.open` if `!S.done`, then `startSite()`, which renders the account menu, calls `pageInit()` if the page defines one (Discover does), and starts `Chat.init()`. `browse.js` sets up its UI and calls `render()` as soon as it loads, before login. `nav.js` calls `Nav.render()` when it loads. The active tab comes from `<body data-page>`.

**Data (`data.js`):** `HOUSES` uses terse keys: `id` short in-page number, `ref` permanent reference number (a random UUID v4, the database key; shown as `DN-` + its first 8 hex digits via `refShort`/`refHTML` in `utils.js`, and Namo finds a listing by it), `n` name, `a` area, `s` school, `d` straight-line km, `t` type, `p` rent (or `null`), `r`/`rc` rating and rating count, `v` verified, `am` amenities, `ds` description, `c` contact, `rev` reviews, `facts` (explicit overrides). The records are real Google Maps places near MSU-IIT. A core product rule: **never invent rent, amenities or rules**. Unknown values stay `null` and are shown as "unverified" or "Rate on request". `SCHOOLS`, `TYPES` and `AMS` drive the selects and chips.

**State (`state.js`):** `S` holds the logged-in user's state: `S.P` preferences, `likes`/`passes`/`marks`/`inq`/`log`/`hist`/`views`, and `S.nn` model weights. Save it with `save()`. `S.P.m[key]` sets how strict each preference is: 0 = don't care, 1 = preferred (affects ranking), 2 = must have (hard filter). `W` holds the ranking weight of each preference and `LBL` its label. The preference keys (`dist budget cap gender water elec env kit wifi space curfew vis`) are shared by `state.js`, `matching.js`, `onboarding.js` (`STEPS`), `chat.js` (`WORDS`) and `twotower.js`. A new preference has to be added in all of them.

**Ranking pipeline:**
- `matching.js`:
  - `facts(h)` pulls facts out of the listing text with regexes; `h.facts` overrides them.
  - `ev(h)` checks each active preference and returns true, false or null (unknown).
  - `score(h)` combines a weighted rule score with the Two-Tower cosine similarity. The blend weight `alpha()` grows with the number of interactions, up to 0.5.
  - A must-have that is false excludes the listing. A must-have that is unknown costs a small penalty.
  - `queue()` builds the Discover deck.
- `twotower.js`: a tiny two-tower network trained in the browser. `dvec(h)` is the listing feature vector and `uvec()` the user vector, which includes the centroids of liked and passed listings. `train()` runs SGD over the recent `S.log` (`{id, y, w}` entries written by `discover.js` actions). Weights start deterministic (`initModel` with `lcg(7)`).

**Accounts (`accounts.js`):** roles: `"student"` (looking for a room, a customer of landowners) and `"owner"` (landowner); one account can be both, chosen at sign-up (`auth.js`) and in the profile, and listing a place makes you a landowner automatically. `Accounts.person(id)` / `people()` / `owners()` return public profiles (name, roles, bio, school, phone only if `showPhone`, joined, places — never email or the hash); `me()` adds the private fields; `updateProfile()`; `describe(p)` is the one-line category ("Landowner · 2 places on DormNamo · also looking for a room"). Everything is in `localStorage` (`dormnamo:accounts`, `dormnamo:session`, `dormnamo:state:<id>`). Passwords are hashed with the pure-JS `argon2id.js` (RFC 9106; tune speed with `DEFAULTS`). Legacy SHA-256 hashes are upgraded to Argon2id on the next login. Guest mode is also supported. To move to a real backend, replace the function bodies in `Accounts` and keep the API.

**Chat (`chat.js` + `talk.js` + `explain.js`):** "Namo" is a local chatbot with no API. It reads English only (Tagalog and Cebuano were removed for cleaner matching; `matching.js` `facts()` still reads local-language words in listing reviews). "What's best for me?", "why?", "why not the second one?" and "compare X and Y" / "which is better?" go to `explain.js`, which writes the answer from the live match data (content selection → sentence planning → varied wording with real minutes, pesos and the student's limits) instead of picking a canned reply; `chat.js` resolves which room is meant (named, "it", "#2", "the next one" via `ordinal()`). **`knowledge.js` (`Know`, loaded before `talk.js`) is Namo's view of every variable on the site:** `find(text)` recognizes listings by full name, short form ("uy pad", "T&D"), unique distinctive word, or a close typo on the distinctive part only (`GENERIC` words like "residence" never match, "best" never becomes "west"); `card(h)` is the full profile (walk, rent, `rating()`, confirmed / not-offered / unknown facts and amenities, hearts, comments, photos, contact, match % and rank); `attrs()`+`answer()` answer any detail, never guessed; `query()` answers questions across listings ("which dorms have wifi under 4k?") without changing `S.P`, and `chat.js` then offers to save them via `ctx.pending.text`; `meHTML()` shows consent, the `dn_prefs` cookie and everything stored; `retrieve()` gives Gemini the relevant listing profiles + preferences as facts. Namo adapts: asking about a listing records a weak interest signal once per visit (`S.views`, `S.log` w 0.3, `train()`), a third ask offers a heart (`ctx.pending.heart`), `S.namo.seen` drives a welcome-back summary, and "remember / forget my preferences" changes consent (`ctx.pending.consent`). `chat.js` handles preferences: it tokenizes and stems the message, fixes typos with Levenshtein distance against its vocabulary, looks words up in `WORDS` (concept → synonyms), matches whole ideas with `PHRASES` ("I'm broke" = cheaper, "online classes" = Wi-Fi), and detects must, skip and negation cues and numbers. Phrase matches always mean "want" so negation inside them ("no water problems") does not flip them. Ordinary words that must never be typo-corrected into a preference ("room" is not "roomy") are registered with no concept. Anything that does not change a preference goes to `talk.js`, which maps words to shared meanings (`CANON`) and picks the closest `INTENTS` example by TF-IDF cosine over meanings, word pairs and character trigrams. A near miss becomes "Did you mean …?". `chat.js` keeps a small `ctx` (the listing being discussed for follow-ups like "does it have wifi?", what "yes" should do next, and the position for "more"). Talk intents with `act` (show, more, prefs, liked, help, yes, no) are carried out by `chat.js`. Meaning rules in `chat.js`: words in `WEAK` ("man", "girl", "power", "share"…) only count when `ROOMCTX` shows the sentence is about a room, or on the one reply right after Namo asked a preference question (`ctx.topic`), so "hey man" or "the man at the gate" never sets gender. Phrase matches add a `WHY` reason that is said back ("Got it, you're on a tight budget…"); `followUp()` asks one missing detail (budget, walk, then must-haves) with Yes/No buttons (`data-say`, handled via `ctx.pending`); a short yes/no after a question answers it; questions with no listing named go to `marketHTML()` (answered from `HOUSES`). `talk.js` scores only examples that share a feature with the message (inverted index `POST`) and memoizes typo repair, as does `chat.js`; about 0.2 ms per reply. `tests/namo.test.mjs` loads all of this into a `vm` with `document` and `localStorage` stubbed out; add a case there when you change how Namo reads messages.

**Web search when there is no good match (`js/namo/websearch.js`, loaded after `knowledge.js`):** when nothing passes the must-haves or the best match is under `GOOD_MATCH` (80%), `chat.js` `webHint()` offers once per visit a "Search the web for more places" button (on match lists and "what's best for me?"); students can also ask ("search online for dorms in Tibanga", `WEB_RX`, area via `areaFrom`, type via `typeFrom`). `WebSearch.run(S.P, {area, type})` queries OpenStreetMap Nominatim (free, no key; one request a second, results cached an hour in `sessionStorage`, "© OpenStreetMap contributors" credit) inside a box of the walking range + 0.5 km (1–5 km) around `SCHOOL_AT[school]` (`data.js`) or the named area, keeps housing only, drops places already in `HOUSES`, and returns each place's type, street, distance, phone and links (its website if mapped, OSM page, Google Maps search) plus "search further" links in two groups: search engines and maps (Google Maps, Google, a Google search limited to social sites, OSM) and social media (Facebook posts, groups and Marketplace, Instagram, TikTok, X, Threads, YouTube, Reddit). Those only open each site's own search; DormNamo never reads those sites. Any Iligan barangay named in the message is used as the area. Rent and rules are never filled in: results say they're unverified. Gemini's Google Search tool is not used because it needs billing (it returns 429 on the free key). Tests: `tests/websearch.test.mjs` and the web-search case in `tests/namo.test.mjs`.

**Gemini wording (optional, FREE tier only):** `js/namo/namo-ai.js` (+ `js/namo/namo-guard.js`, both loaded before `talk.js`) can ask Google Gemini, through the worker's `POST /namo` (`worker/namo.mjs`, routed from `nearby.mjs`), to reword Namo's answers. Namo still decides everything: `reply()` stays synchronous and only leaves an `aiJob` (explanations from `explain.js` in "explain" mode; small talk it didn't understand in "chat" mode, where no facts are allowed). `ask()` then tries Gemini and falls back to Namo's own wording on any failure. Every reply is fact-checked twice by `NamoGuard.check()` (worker: numbers, prices, claims; browser: the same plus listing names); a reply that adds anything is never shown. It runs only when `DN_CONFIG.nearbyApiUrl` is set, `DN_CONFIG.namoAI` isn't false (`NAMO_AI=off`), and the student said yes (`S.ai`; the question explains that free-tier content may be used by Google). The system prompt lives only on the worker. Keys: `GEMINI_API_KEY` worker secret from a Google AI Studio project **with no billing**, so nothing can be charged (past the quota Google returns 429 → fallback); `GEMINI_MODEL` (default `gemini-3.5-flash-lite`), `NAMO_DAILY_LIMIT`, `NAMO_PER_IP`; plus a 60/day per-browser cap. Tests: `tests/namo-guard.test.mjs`, `tests/namo-worker.test.mjs` (Gemini mocked), and the Gemini case in `tests/namo.test.mjs`.

**Learning from activity (`js/matching/insights.js`, every page, just before `main.js`):** only with consent. Namo asks once (`Insights.askHTML()`, buttons `data-consent`); the answer is `S.learn` (undefined = not asked). With a yes it records rooms opened and seconds spent (`S.act.v`, by wrapping `open()` and the dialog's close event) and settled Rooms filters (`S.act.q`, from `browse.js` `render()`), and `profile()` combines them with likes/hearts, bookmarks, inquiries and passes into typical rent, walk, room type, favored features and what they skip. "what do I like?" shows `summaryHTML()` and offers `suggestions()`; "stop learning" sets `S.learn = false` and deletes `S.act`. It never reads anything outside DormNamo (browsers don't allow reading other sites' cookies or history, and Namo doesn't try).

**Maps and nearby places:** there are two providers, chosen automatically. With no `js/app/config.js` keys (the current setup), the map is Leaflet + OpenStreetMap tiles and nearby places come from OpenStreetMap via Overpass. With keys, Google is used.
- Dorm coordinates come from `js/data/pins.js` (`PINS`, set by hand in `pin.html`), drafts in `localStorage` (`dn:pinDrafts`, shown only on that device), or `lat`/`lng` in `data.js`. `DNMaps.applyPins()` merges them at load, and pins win.
- `npm run nearby` (`tools/osm-snapshot.mjs`) saves OSM results per pinned dorm into `js/data/nearby-snapshot.js`, which is used when the pin hasn't moved. Live Overpass is only a fallback, because the public servers are slow (~25 s) and often return 502/504.
- `details.js` defines a global `open(id)`, which shadows `window.open`. To open a URL, create an `<a target=_blank>` and click it (`openLink` in maps.js).

- `js/maps/nearby-core.js` holds pure logic: `CATEGORIES` (Places types, radius, color, icon), distance and time formatting, the summary text, and an opening-hours check.
  - It is a UMD file. The browser gets the `NearbyCore` global, while the worker and the tests `import` it as CommonJS, so keep it free of the DOM and of ES-module syntax.
- `js/maps/maps.js` (`DNMaps`): `details.js` calls `DNMaps.section(h)` while building the dialog HTML and `DNMaps.mount(h)` after `showModal()`.
  - **One** `google.maps.Map` is created per page and its canvas is moved into each dialog, because every new Map is a billed load.
  - Nearby data is memoized per listing and kept in `sessionStorage` for 1 h.
  - Everything fails soft: no key, no coordinates or a worker error shows a message, and the dialog still works.
- `worker/nearby.mjs` is the only backend: a Cloudflare Worker with `GET /nearby?lat&lng`.
  - It makes one Places API (New) Nearby Search per category, with optional Routes API times, and keeps a TTL cache in `worker/cache.mjs` (KV or memory).
  - `createHandler({fetch, store, now})` injects dependencies, which is how `tests/worker.test.mjs` mocks Google.
- `tools/geocode.mjs` edits `data.js` line by line through `tools/geo-lib.mjs`. Each listing must stay on one line as a JSON object.
  - The `geo` field records the source (`places`, `geocode:<type>` or `manual`) and `geoAt` the date. Coordinates from Google are refreshed after 30 days (Google's caching terms). `manual` ones are never touched.

**Photos (`js/listings/photos.js`):** cover and room photos are kept apart. `Photos.split(h)` → `{cover, rooms}` (photo `kind: "cover"|"room"`; untagged = first is the cover). `Photos.thumb(h)` (cards) and `Photos.hero(h)` + `Photos.mount(D, h)` (dialog header) show only the cover (else the first room photo); `Photos.rooms(h)` + `Photos.mountRooms(D, h)` are the dialog's own "Room photos" grid with a full-size viewer (a nested `<dialog class="rp-view">`). My listings edits them in two separate cards. Dorms without `PHOTOS.dorm[id]` fall back to CC BY-SA area photos, which must stay labeled "Area photo" and keep their credit/license links. Never add photos scraped from Google Maps or Facebook.

**CSS:** `base.css` is the design system. Load order (same on both pages): `base`, `home`, `chat`, `ui`, `discover`, `maps`, `details`, `polish` (blue/yellow palette and final fixes), `hero`, `brand`, `onboarding`, then `owners` and `finder` on `index.html` only, and **`css/base/mobile.css` last on every page** (phone and touch fixes only: 16px form fields so iPhones don't zoom, full-width dialogs, compact Compare, the docked My listings save bar, a small Namo preview). Check phones at 360 and 390 px wide: no page may scroll sideways. A styled dropdown's hidden native `<select>` (`.dd-native`, hero.css) must take no space, or it pushes the page wider than the screen. A later file wins at equal specificity, so `polish.css` does not override `hero`/`brand`/`onboarding`/`finder`. `body.dark` styles the Discover page.

**Owner listings (`js/listings/listings.js`, every page, right after `photos.js`):** places owners add (Rooms "Add your property" form or `mylistings.html`) live in `localStorage` (`dormnamo:listings`, one record per place with `ref` (UUID v4, given on save; older records get one once at load), `uid`, the HOUSES fields, `facts`, `plan`, `cover` and `photos` as JPEG data URLs). At load `Listings.apply()` merges every record into `HOUSES` and its photos into `PHOTOS.dorm`, so cards, Discover and the dialog need no special cases. Photos are shrunk in the browser (`Listings.shrink`, ~1100–1400 px, JPEG .74) because localStorage holds about 5 MB; `save()` returns `{error: "full"}` when it is out of space. Owners only set `facts` they state; "Not stated" deletes the key so it stays unknown. `mylistings.js` edits a working copy and writes only on Save (Ctrl+S); `#<id>` picks a listing, `#new` starts one. The account menu links to the page (`nav.js`). Phone helpers (`fmtPhone`, `phoneOk`, `phoneField`, `PHONE_MSG`) are in `utils.js`: numbers are always `09XX XXX XXXX` (+63 / 63 / 9… are converted to 09; nothing else is accepted). Locations: `data.js` has `PH_PLACE` (Iligan City, Lanao del Norte, Region X (Northern Mindanao), ZIP 9200) and the 44 `BARANGAYS`; both owner forms use a barangay `<select>` (`barangayOptions`) + optional street/purok and save `brgy`, `street`, `a` (= the barangay, shown on cards) and `addr` (`fullAddress(street, brgy)`); `placeLineHTML()` shows the fixed part; `barangayOf()` normalizes ("brgy. tibanga" → "Tibanga").

**Comments (`js/listings/comments.js`, every page, loaded after `listings.js`):** per-listing student comments in the details dialog (`Comments.section(h)` + `Comments.mount(D, h)`, after the map) and a count badge on Rooms cards (`Comments.counts()`, `[data-cm]`). Stored in `localStorage` (`dormnamo:comments`), so they only exist in the browser that wrote them; only the author (`uid === USER.id`) can delete. Swap `load`/`store`/`add`/`remove` for a backend and keep the API.

**Stars vs hearts (keep them separate):** stars rate *quality* and only come from people who stayed there: `rating(h)` in `utils.js` blends the Google rating (`h.r` × `h.rc`) with tenant ratings left on comments (`Comments.stats`, one per person, latest wins; owners can't rate their own listing). `stars(h, long)` renders them with `[data-rate]` so `refreshStars(h)` can update them, and "Top rated" sorts by `ratingScore(h)`. Hearts (`js/listings/hearts.js`, every page after `comments.js`) mean *saved / popular*: a heart is the same as a Discover like (`S.likes` + an `S.log` entry), the per-room count lives in `localStorage` (`dormnamo:hearts`), and hearts never change the star score. Hearts are red, stars gold. `main.js` calls `Hearts.syncAll()` after login; `discover.js` calls `Hearts.sync(id)` on like/undo.

**Messages (`js/account/inbox.js`, every page right after `hearts.js`; page: `messages.html` + `js/pages/messages.js`):** `Inbox` stores conversations in `localStorage` (`dormnamo:inbox` = {threads, msgs}), so like accounts they only exist in this browser; swap `load`/`store`/`on` for a backend and keep the API. A "dm" is one-to-one: `Inbox.interest(listingId)` (the dialog's "I'm interested · Message" in `details.js` `ownerHTML`) opens it with the place's landowner (`Inbox.ownerOf`: only owner-listed places have one; Google Maps places don't) and posts an "interest" card. Deal status: inquiry → negotiating (any `offer` {rent, move, note}; a newer offer replaces the open one) → agreed (the other side `answer`s yes) or declined (`close`, landowner only). Agreed adds the student to the place's "group" chat (one per listing, roles owner/tenant; the landowner can remove tenants, tenants can `leave`). `Inbox.on(fn)` fires on changes, including other tabs (`storage` event). Messages can carry up to 4 photos (`data.imgs`, shrunk with `Listings.shrink` to ~900 px JPEG; `send()` returns `{error: "full"}` when browser storage is full) and emojis (a picker in the composer; emoji-only messages show large); photos open in a viewer, can be pasted. **Inquire now** (`details.js` `inquireBtn`, next to the price): owner-listed places open the chat (`startInterest`); Google Maps places (no account) open a panel to call / text the listed number (shown as 09…) with an editable ready message, Copy, Facebook and Google Maps links. **Test bot** (`js/account/testbot.js`, every page after `inbox.js`): "Try it with a test bot" on Messages creates `bot-landowner` (`Accounts.addBot`, `bot: true`, no password, labeled "Test bot"), one clearly marked test listing (id 990001) and a chat; `TestBot.reply()` (pure) answers questions, photos (sends a canvas-drawn room picture), emojis and offers (counters below ₱2,800 once, accepts at or above), and welcomes new tenants in the group; it posts via the `as` argument of `Inbox.send/offer/answer`, which only accepts `bot-` ids. "Remove test bot" deletes the account, listing and chats (`Inbox.forget`). Tests: `tests/testbot.test.mjs`. The nav "Messages" tab shows `Inbox.unread()` (`Nav.unread`), and `main.js` has Namo point to unread messages. `people.html` + `js/pages/people.js` show your account (edit form) and all accounts grouped as Landowners / Students / Everyone, `#u=<id>` opens a profile. Tests: `tests/inbox.test.mjs`.

**Owners (`owners.js`, index only):** "List your place" pricing. `BOOST`/`PRO` prices must stay in sync with the `<select id="aPlan">` options in `index.html`. Yearly Owner Pro follows the monthly pricing pattern: ₱4,788 = ₱399/month (charm price), "Save 20%" badge, the monthly price struck through as the anchor, and the value of the included boosts.

**Compare (`browse.js` `showCompare`):** up to 3 places in `#dlg` (class `cmp-wide`), grouped rows (match, cost and place, quality, the student's active preferences via `ev()`, details), a gold "Best" mark where one value clearly wins (`cmpBest`), unknowns stay "Unknown". Styles in `css/pages/finder.css`.

**Namo notifications (`chat.js`):** every bot message said while the chat is closed counts as unread: red badge on the Ask Namo button, `(n)` in the tab title, and a preview bubble (`#chatPeek`) that opens the chat. The greeting only counts until the chat was opened once in the tab (`sessionStorage` `dormnamo:namoOpened`). `Chat.notify(html)` lets other code alert the student; `Chat.refresh()` (after editing preferences) announces a new best match.

## Conventions

- Page titles read `DormNamo | <Page>` (a vertical bar, not a dash or dot).
- Escape any user- or data-derived string with `esc()` before putting it into the `innerHTML` strings that build most of the UI.
- Code is formatted with Prettier (`npx prettier --write --print-width 110` on `css/`, `js/`, `tools/`, `tests/`, `worker/`). Never format `js/data/data.js` (the geocode tool needs one listing per line) or the generated `js/data/pins.js`, `js/data/nearby-snapshot.js` and `js/app/config.js` (a `--ignore-path` file did not stop Prettier from rewriting them, so restore them if touched). The four HTML files are formatted the same way (Prettier's default whitespace handling keeps inline spacing).
- Keep the existing `var`, function expressions and no transpile-only syntax. Do not add a framework or a build step. (The worker and the tools are modern ES modules, `.mjs`.)
- UI icons are line SVGs from `ico(name)` (`ICONS` in `utils.js`) and the logo is `logoHTML()`. Don't use emoji in navigation, buttons or cards. Namo's chat replies may keep them. Brand/Discover styles live in `css/base/brand.css`.
- Rooms hero motion lives in `js/pages/hero-fx.js` + the end of `css/pages/hero.css`: the grid spotlight (`--mx/--my` on `.hero`), stat scramble, and the intro. `index.html` adds `class="intro"` to `<html>` in the head (hidden until `HeroFX.play()` runs from `startSite()`, with an 8 s fallback). Keep new hero children compatible with the `.hero .wrap > *` intro animation.
- `base.css` pads every `<section>` by 48px. Only the page sections want that, so any other `<section>` (the dialog's `.nb`, the pin tool's main column, Leaflet's layer switcher) must reset `padding`.
- Speed metrics: never start the whole page or the hero `h1` (the Largest Contentful Paint element) fully transparent or animated. Browsers only count animated or opacity-0 content as painted on a later repaint. The body fade starts at `opacity: .01` for that reason. This took FCP/LCP on the Rooms page from ~1.1 s/2.4 s to ~0.15 s.
- Glides to the room list go through `FX.resultsTarget(finder)`. On phones it targets the results bar, because the filter panel fills the first screen there.
- Fonts load as variable ranges (`Figtree:wght@400..800`, `Bricolage+Grotesque:wght@600..800`). Keep every weight used in CSS inside those ranges.
- Walking routes: clicking a nearby place (pin or list name) calls `routeTo()` in `maps.js`. It draws a dashed straight line at once, then the real path from the free OSRM routers (FOSSGIS `routed-foot` first, the OSRM demo car profile as backup with walking time estimated at 4.8 km/h), with the result in the `#nbRoute` bar under the map. No bubble, because it covered the route. Routes are memoized and kept in `sessionStorage`; `routeToken` drops stale responses. Parsing (`routeUrl`/`parseRoute`/`routeLabel`) is in `nearby-core.js` with tests. The routers ask for fair use and the "Routes © FOSSGIS / OSRM" credit.
- "Find your room" styles live in `css/pages/finder.css`. Every visible `<select>` (search bar, filter "Near", "Sort by", and the owner form's Room type/Near/Plan) uses the custom `Dropdown` (`js/app/select.js`, ids listed at its end); a new select should be added there too. When code sets a select's value, call `Dropdown.sync(select)` (browse.js `ddSync`) or the styled button shows the old choice. Set the price filter only through `setPrice(v)`, which keeps `F.p`, the slider, its `--fill` and the label in step.
