# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Running

Static site, no build step, no linter. Pages: `index.html` at the root (Rooms, `ktens.me/DormNamo/`), and one folder per other page with its own `index.html`: `discover/` (swipe feed), `my-listings/` (owners edit their listings), `people/` (accounts: landowners and students), `messages/` (chats), `about/` (About us: mission, how matching works, the five developers in `about.js` `TEAM`: name, role, bio, focus, optional photo, and `links` to GitHub / Facebook / X / Instagram / LinkedIn, drawn with the `s-*` icons in `utils.js`; only `https://` links become links, "" shows a dimmed placeholder, a missing key hides that network) and `pin/` (the pin tool). Use VS Code Live Server (or any web server) so `/discover/` opens its `index.html`; from `file://` the links name `index.html` explicitly. Deploy by uploading the folder to GitHub Pages; `404.html` forwards the old addresses (`discover.html`, `people.html#me`…) to the folders. `package.json` exists only for tooling, not for the site. The tools need Node ≥ 21.7 (they use `process.loadEnvFile`):

- `npm test`: Node's built-in test runner (`node --test tests/`), no dependencies. Run one file with `node --test tests/worker.test.mjs`, or one test with `node --test --test-name-pattern="cache expires" tests/`.
- `npm run config`: writes `shared/js/app/config.js` (Maps browser key, Map ID, worker URL, Supabase URL + anon key) from `.env`. It is committed and deployed, so it must only ever hold public values; run it and commit the result after changing `.env`.
- `npm run nearby [-- --all]`: saves OpenStreetMap nearby places for pinned dorms into `shared/js/data/nearby-snapshot.js` (no key).
- `npm run geocode [-- --dry-run|--force|--max-age-days N]`: saves `lat`/`lng` into `shared/js/data/data.js` (needs `GOOGLE_MAPS_SERVER_KEY`).
- `npm run worker:dev` / `npm run worker:deploy`: the Cloudflare Worker through `npx wrangler`.
- `npm run db:bundle`: joins `supabase/migrations/*.sql` into `supabase/setup.sql` (pasted into Supabase's SQL editor). `npm run db:test`: runs the migrations on PGlite (a real Postgres in Node; the one dev dependency, `npm install` once) with stand-ins for Supabase's `auth`/`storage`, and checks 38 rules. Run both after changing a migration.

Never put a real key in source. Keys live in `.env` (gitignored); `.env.example` documents them. The Supabase anon key is browser-safe (RLS protects the data); the service_role key never goes in the site, only Edge Functions get it (Supabase provides it).

## Architecture

**Layout (grouped by function):** each page is a folder holding its `index.html` and the CSS/JS only it uses (`discover/`, `my-listings/`, `people/`, `messages/`, `about/`, `pin/`); Rooms is `index.html` at the root with its own files in `home/` (`browse.js`, `owners.js`, `hero-fx.js`, `finder.css`). Everything two or more pages load lives in `shared/js/{app,account,data,listings,matching,maps,namo}/` and `shared/css/{base,components}/` (including `home`, `hero`, `discover` and `owners` css, which several pages load). `shared/js`, `shared/css`, `tools`, `worker` and `tests` each have a `README.md` with a one-line purpose per file. File names below are given without their folder. Node tools and tests find browser scripts through `tools/js-files.mjs` (`jsPath("data")` → `shared/js/data/data.js`), so moving a file means updating that map (`FOLDERS` for shared, `PAGES` for page code), the `<script>`/`<link>` tags in every app page (and `pin/index.html` if it loads the file), and the folder README. Pages in folders reach shared files with `../shared/…`. **Never hard-code a page or image address in JS:** use `pageUrl(id, hash)` (ids as in `<body data-page>`: `home`, `discover`, `listings`, `people`, `messages`, `about`, `pin`; `PAGE_DIR` in `utils.js`), `asset("img/…")` for site files, and `samePath(a, b)` to compare page paths (`/` = `/index.html`). `SITE_ROOT` comes from `utils.js`'s own script address, so they work from any folder; the consent cookies use its path, so every page shares them. Tests: `tests/site-urls.test.mjs`. The brand kit (`brand-assets`: logo, icons, Namo avatar, palette, fonts) and the video ad (Remotion + React, with its own CLAUDE.md) are separate folders outside this repo, not used by the site. The kit was generated from `LOGO_MARK`, `ICONS` and the colour tokens, and the ad copies listing facts from `data.js` (`ROOMS` in its `src/brand.jsx`), so update them when those change. `match-formula.txt` at the root explains the match % in plain words; update it when `W`, `score()` or `alpha()` change.

Plain ES5-style browser JS. There are no modules: every file defines globals (`HOUSES`, `S`, `USER`, `$`, `esc`, `score`, `draw`, …) or an IIFE namespace (`Accounts`, `Auth`, `Onboarding`, `Nav`, `FX`, `Chat`, `Argon2id`). **Script order in each HTML file is the dependency graph.** If you add a file or a global, add the `<script>` tag to `index.html` and `discover/`, `my-listings/`, `people/`, `messages/` and `about/` `index.html` in the right place. Page-only scripts: `browse.js`, `owners.js` and `hero-fx.js` load only on Rooms (`index.html`), and every other page script only on its own folder's page (`about/` otherwise loads the same scripts as `people/`), and `select.js` on every app page except Discover, so shared code must guard them (`if (window.HeroFX) …`, `if (window.Dropdown) …`). Most page scripts load after `chat.js`, just before `insights.js`/`main.js`; `browse.js`/`owners.js` load right after `details.js` and `discover.js` right after `state.js`. `pin/index.html` has its own short list (`data`, `utils`, `pins`, `nearby-core`, `maps`, `pin-tool`). `shared/js/app/config.js` is generated by `npm run config`, committed (public values only) and loaded by every page; `shared/js/app/config.example.js` is the template, and the code must work when it is missing or empty. Every app page also needs the same overlay/dialog elements (`#auth`, `#ob`, `#toast`, `#dlg`).

**Consent first (`shared/js/app/consent.js`, right after `utils.js` on every app page):** `boot()` first calls `Consent.show(boot)` until the student has chosen. "Accept preference cookies" → `Accounts.saveState` writes `localStorage` and `save()` also writes the `dn_prefs` cookie (school, walk, budget, must-haves; 180 days, `Path` = this site's folder, `SameSite=Lax`, `Secure` on https), which `browse.js` reads on load to start the Rooms search from them. "Essential only" → state lives only in `sessionStorage` for this tab and `Accounts.forgetStates()` deletes saved states and the cookie. Always kept: accounts, the session and the choice (`dn_consent` cookie, mirrored in `localStorage` because `file://` ignores cookies). Changeable from the account menu ("Privacy & cookies"). GitHub Pages never reads cookies server-side; only the site's JS does. Insights (learning) and Gemini keep their own separate consent. Tests: `tests/consent.test.mjs`.

**Start-up (`main.js`):** `boot()` → `Accounts.current()`. With no session it calls `Auth.show(boot)`. With a session it runs `loadState(user)`, then shows `Onboarding.open` if `!S.done`, then `startSite()`, which renders the account menu, calls `pageInit()` if the page defines one (Discover does), and starts `Chat.init()`. `browse.js` sets up its UI and calls `render()` as soon as it loads, before login. `nav.js` calls `Nav.render()` and `Nav.footer()` when it loads; the footer (`FOOT` columns Students / Landowners / DormNamo, then a bottom bar with ©, Privacy, language and PHP; no social or GitHub links, since the repo is private) fills `<footer id="siteFooter" class="site-foot">` on every page except Messages (full-height chat). Footer links go only to things that exist; `data-foot` buttons open Namo or the cookie choice. Use `<div>` columns there, not `<nav>`: base.css styles every `nav` as the header bar. The active tab comes from `<body data-page>`.

**Data (`data.js`):** `HOUSES` uses terse keys: `id` short in-page number, `ref` permanent reference number (a random UUID v4, the database key; shown as `DN-` + its first 8 hex digits via `refShort`/`refHTML` in `utils.js`, and Namo finds a listing by it), `n` name, `a` area, `s` school, `d` straight-line km, `t` type, `p` rent (or `null`), `r`/`rc` rating and rating count, `v` verified, `am` amenities, `ds` description, `c` contact, `rev` reviews, `facts` (explicit overrides). The records are real Google Maps places near MSU-IIT. A core product rule: **never invent rent, amenities or rules**. Unknown values stay `null` and are shown as "unverified" or "Rate on request". `SCHOOLS`, `TYPES` and `AMS` drive the selects and chips.

**State (`state.js`):** `S` holds the logged-in user's state: `S.P` preferences, `likes`/`passes`/`marks`/`inq`/`log`/`hist`/`views`, and `S.nn` model weights. Save it with `save()`. `S.P.m[key]` sets how strict each preference is: 0 = don't care, 1 = preferred (affects ranking), 2 = must have (hard filter). `W` holds the ranking weight of each preference and `LBL` its label. The preference keys (`dist budget cap gender water elec env kit wifi space curfew vis`) are shared by `state.js`, `matching.js`, `onboarding.js` (`STEPS`), `chat.js` (`WORDS`) and `twotower.js`. A new preference has to be added in all of them.

**Ranking pipeline:**
- `matching.js`:
  - `facts(h)` pulls facts out of the listing text with regexes; `h.facts` overrides them.
  - `ev(h)` checks each active preference and returns true, false or null (unknown).
  - `score(h)` combines a weighted rule score with the Two-Tower cosine similarity. The blend weight `alpha()` grows with the number of interactions, up to 0.5.
  - A must-have that is false excludes the listing. A must-have that is unknown costs a small penalty.
  - `queue()` builds the Discover deck.
- Discover (`discover.js` cover flow): the focused room (`Q[pos]`) sits in the middle and up to 3 ranked neighbours stack behind it on each side, smaller, dimmed and blurred (`put()`/`lay()` set transform, filter, opacity inline). Sideways drag / arrow keys / sideways trackpad scroll browse (`go()`), one room per swipe: the finger moves a whole card per ~60% of a card width (`per`, not the ~30 px visual gap `metrics().s1`), the strip resists past the next room, flicks use the speed of the last ~100 ms (`speed()`), and one trackpad gesture moves one room (`spent`), swipe or arrow up likes and down passes (`decide()`): the card leaves vertically and the neighbour glides in; `want` keeps that room focused after `draw()` re-ranks. Only the focused card uses `touch-action: none` (the deck is `pan-y`), so up/down on it means like/pass while the page still scrolls from the side cards and the space around them; on phones `fitDeck()` sizes the deck from the visible height so the room, `#dPos` and the rail fit on one screen above the Ask Namo corner. `--lk`/`--ps` light the Like/Pass label and the side guides (`.dguide`). Side cards also tilt (`rotateY`, `perspective` on the deck) and `#dPos` shows the position (03 / 24), flanked on screens under 1180 px by small plain-text Like/Pass hints (`.dph`; not `.dh`, which is the details dialog header in `base.css`); at 1180 px and up a thin arrow + one word (`.dguide`, no box) sits on each side instead, and `nudge()` bobs the first card once per tab on those screens. The header is TikTok-style tabs (`Saved | For you`, `tab()` toggles `.on-saved`, which swaps the strip for the liked & bookmarked list) plus a preferences icon (`#dPref`). `.dpage` and `.deckwrap` need explicit `grid-template-columns: minmax(0, 1fr)`: an auto track shrinks to the rail and squeezes the deck to ~270 px.
- `twotower.js`: a tiny two-tower network trained in the browser. `dvec(h)` is the listing feature vector and `uvec()` the user vector, which includes the centroids of liked and passed listings. `train()` runs SGD over the recent `S.log` (`{id, y, w}` entries written by `discover.js` actions). Weights start deterministic (`initModel` with `lcg(7)`).

**Accounts (`accounts.js`):** roles: `"student"` (looking for a room, a customer of landowners) and `"owner"` (landowner); one account can be both, chosen at sign-up (`auth.js`) and in the profile, and listing a place makes you a landowner automatically. `Accounts.person(id)` / `people()` / `owners()` return public profiles (name, roles, bio, school, phone only if `showPhone`, joined, places — never email or the hash); `me()` adds the private fields; `updateProfile()`; `describe(p)` is the one-line category ("Landowner · 2 places on DormNamo · also looking for a room"). **Two modes, same API:** with Supabase configured (`DB.enabled()`), `Accounts.init()` (awaited by `boot()` in `main.js`; resolves `false` at once without config) loads your `profiles` row and the `public_profiles` directory into memory, so `current()`/`me()`/`person()`/`people()` stay synchronous; `signUp` = Supabase Auth with `{name, roles}` metadata (the `handle_new_user` trigger makes the profile; with email confirmation on it rejects with `err.info = true` and Auth shows it as good news), `logIn` = `signInWithPassword`, `updateProfile` updates `profiles` (`show_phone` is the column), `logOut()` returns a promise (wait before reloading), `resetPassword` / `recovering()` / `setPassword` drive Forgot password and the reset-link screen (`Auth.reset`), `deleteAccount()` calls the Edge Function. Supabase errors become sentences in `authMessage()`; never show raw server text. The session record gets `cloud: true`; a leftover this-browser session is logged out once and its saved state is carried to the new login (`dormnamo:carry`). Test bots stay local in both modes, and saved state (`loadState`/`saveState`) is still per browser until it moves to `user_state`. Without config (or if supabase-js fails to load) it's the original local mode: Everything is in `localStorage` (`dormnamo:accounts`, `dormnamo:session`, `dormnamo:state:<id>`). Passwords are hashed with the pure-JS `argon2id.js` (RFC 9106; tune speed with `DEFAULTS`). Legacy SHA-256 hashes are upgraded to Argon2id on the next login. Guest mode is also supported. To move to a real backend, replace the function bodies in `Accounts` and keep the API.

**Chat (`chat.js` + `talk.js` + `explain.js`):** "Namo" is a local chatbot with no API. It reads English only (Tagalog and Cebuano were removed for cleaner matching; `matching.js` `facts()` still reads local-language words in listing reviews). "What's best for me?", "why?", "why not the second one?" and "compare X and Y" / "which is better?" go to `explain.js`, which writes the answer from the live match data (content selection → sentence planning → varied wording with real minutes, pesos and the student's limits) instead of picking a canned reply; `chat.js` resolves which room is meant (named, "it", "#2", "the next one" via `ordinal()`). **`knowledge.js` (`Know`, loaded before `talk.js`) is Namo's view of every variable on the site:** `find(text)` recognizes listings by full name, short form ("uy pad", "T&D"), unique distinctive word, or a close typo on the distinctive part only (`GENERIC` words like "residence" never match, "best" never becomes "west"); `card(h)` is the full profile (walk, rent, `rating()`, confirmed / not-offered / unknown facts and amenities, hearts, comments, photos, contact, match % and rank); `attrs()`+`answer()` answer any detail, never guessed; `query()` answers questions across listings ("which dorms have wifi under 4k?") without changing `S.P`, and `chat.js` then offers to save them via `ctx.pending.text`; `meHTML()` shows consent, the `dn_prefs` cookie and everything stored; `retrieve()` gives Gemini the relevant listing profiles + preferences as facts. Namo adapts: asking about a listing records a weak interest signal once per visit (`S.views`, `S.log` w 0.3, `train()`), a third ask offers a heart (`ctx.pending.heart`), `S.namo.seen` drives a welcome-back summary, and "remember / forget my preferences" changes consent (`ctx.pending.consent`). `chat.js` handles preferences: it tokenizes and stems the message, fixes typos with Levenshtein distance against its vocabulary, looks words up in `WORDS` (concept → synonyms), matches whole ideas with `PHRASES` ("I'm broke" = cheaper, "online classes" = Wi-Fi), and detects must, skip and negation cues and numbers. Phrase matches always mean "want" so negation inside them ("no water problems") does not flip them. Ordinary words that must never be typo-corrected into a preference ("room" is not "roomy") are registered with no concept. Anything that does not change a preference goes to `talk.js`, which maps words to shared meanings (`CANON`) and picks the closest `INTENTS` example by TF-IDF cosine over meanings, word pairs and character trigrams. A near miss becomes "Did you mean …?". `chat.js` keeps a small `ctx` (the listing being discussed for follow-ups like "does it have wifi?", what "yes" should do next, and the position for "more"). Talk intents with `act` (show, more, prefs, liked, help, yes, no) are carried out by `chat.js`. Meaning rules in `chat.js`: words in `WEAK` ("man", "girl", "power", "share"…) only count when `ROOMCTX` shows the sentence is about a room, or on the one reply right after Namo asked a preference question (`ctx.topic`), so "hey man" or "the man at the gate" never sets gender. Phrase matches add a `WHY` reason that is said back ("Got it, you're on a tight budget…"); `followUp()` asks one missing detail (budget, walk, then must-haves) with Yes/No buttons (`data-say`, handled via `ctx.pending`); a short yes/no after a question answers it; questions with no listing named go to `marketHTML()` (answered from `HOUSES`). `talk.js` scores only examples that share a feature with the message (inverted index `POST`) and memoizes typo repair, as does `chat.js`; about 0.2 ms per reply. `tests/namo.test.mjs` loads all of this into a `vm` with `document` and `localStorage` stubbed out; add a case there when you change how Namo reads messages.

**Web search when there is no good match (`shared/js/namo/websearch.js`, loaded after `knowledge.js`):** when nothing passes the must-haves or the best match is under `GOOD_MATCH` (80%), `chat.js` `webHint()` offers once per visit a "Search the web for more places" button (on match lists and "what's best for me?"); students can also ask ("search online for dorms in Tibanga", `WEB_RX`, area via `areaFrom`, type via `typeFrom`). `WebSearch.run(S.P, {area, type})` queries OpenStreetMap Nominatim (free, no key; one request a second, results cached an hour in `sessionStorage`, "© OpenStreetMap contributors" credit) inside a box of the walking range + 0.5 km (1–5 km) around `SCHOOL_AT[school]` (`data.js`) or the named area, keeps housing only, drops places already in `HOUSES`, and returns each place's type, street, distance, phone and links (its website if mapped, OSM page, Google Maps search) plus "search further" links in two groups: search engines and maps (Google Maps, Google, a Google search limited to social sites, OSM) and social media (Facebook posts, groups and Marketplace, Instagram, TikTok, X, Threads, YouTube, Reddit). Those only open each site's own search; DormNamo never reads those sites. Any Iligan barangay named in the message is used as the area. Rent and rules are never filled in: results say they're unverified. Gemini's Google Search tool is not used because it needs billing (it returns 429 on the free key). Tests: `tests/websearch.test.mjs` and the web-search case in `tests/namo.test.mjs`.

**Gemini wording (optional, FREE tier only):** `shared/js/namo/namo-ai.js` (+ `shared/js/namo/namo-guard.js`, both loaded before `talk.js`) can ask Google Gemini, through the worker's `POST /namo` (`worker/namo.mjs`, routed from `nearby.mjs`), to reword Namo's answers. Namo still decides everything: `reply()` stays synchronous and only leaves an `aiJob` (explanations from `explain.js` in "explain" mode; small talk it didn't understand in "chat" mode, where no facts are allowed; also a near miss, where Gemini answers the message and Namo's guess stays under it as `job.extra` "Or did you mean …? Just say yes.", `ctx.pending` still set). `ask()` then tries Gemini and falls back to Namo's own wording on any failure. Every reply is fact-checked twice by `NamoGuard.check()` (worker: numbers, prices, claims; browser: the same plus listing names); a reply that adds anything is never shown. It runs only when `DN_CONFIG.nearbyApiUrl` is set, `DN_CONFIG.namoAI` isn't false (`NAMO_AI=off`), and the student said yes (`S.ai`; the question explains that free-tier content may be used by Google). The system prompt lives only on the worker. Keys: `GEMINI_API_KEY` worker secret from a Google AI Studio project **with no billing**, so nothing can be charged (past the quota Google returns 429 → fallback); `GEMINI_MODEL` (default `gemini-3.5-flash-lite`), `NAMO_DAILY_LIMIT`, `NAMO_PER_IP`; plus a 60/day per-browser cap. Tests: `tests/namo-guard.test.mjs`, `tests/namo-worker.test.mjs` (Gemini mocked), and the Gemini case in `tests/namo.test.mjs`.

**Supabase backend (`supabase/`, see its README):** the database for shared data. `migrations/` are idempotent (the first schema was made by hand in the SQL editor; they only add what's missing, never drop data), numbered 01 tables → 02 accounts → 03 listings and plans → 04 messaging → 05 comments, hearts, state → 06 storage → 07 grants → 08 descriptions (comment on every table and column; add one for anything new). Rules live on the server, not just in the browser: you read only your own `profiles` row (others use the `public_profiles` view: no email, phone only with `show_phone`); `check_listing_quota` refuses a new listing past 2 (Basic) / 5 (active `subscriptions` row) with `listing_limit` and adds the owner role; `plan`, `f`, `owner_id`-on-update, `subscriptions` and `boosts` are not granted to the browser (only the team via `admin.sql` or a future payment Edge Function writes them); 3 Featured boosts per barangay (`no_featured_spots`); threads are read-only to members and every deal change goes through functions whose full-rights bodies live in the API-hidden `private` schema behind same-named `security invoker` wrappers in `public` (keep that pattern for any new definer function, and `private.listing_limit` stays internal; `db:test` fails on a callable definer function or definer view in `public`, or an unindexed foreign key) (`start_interest`, `start_dm`, `send_offer`, `answer_offer`, `close_thread`, `leave_group`, `remove_tenant`, `mark_read`; members may insert only `text`/`photo` messages); one star rating per person per place, none for your own (`comment_rules`); Realtime on `messages` and `threads`; buckets `listing-photos` (public, `<uid>/…`) and `chat-photos` (members only, `<thread id>/…`). Errors are raised as bare snake_case codes; keep it that way, because `DB.code()` only passes `^[a-z_]+$` through and `DB.message()` maps them to sentences. `functions/delete-account` deletes a login (needs the service role). When you add a table, column, function or rule: write a new migration (or extend one, keeping it re-runnable), grant it in 07, add a check to `supabase/tests/rules.mjs`, then `npm run db:bundle` and `npm run db:test`. **Browser side:** `shared/js/app/db.js` (`DB`, every app page right after `config.js`) loads supabase-js 2.119.0 from jsDelivr only when `DN_CONFIG.supabaseUrl`/`supabaseKey` are set (`DB.ready()` → client or null, `DB.rpc()`, `DB.deleteAccount()`); with no config the site keeps using browser storage. Modules move onto it one at a time keeping their API: Accounts (done) → Listings + photos → user_state → Inbox → Comments → Hearts. Tests: `tests/db.test.mjs`, `tests/accounts-cloud.test.mjs` (a stand-in for supabase-js).

**Learning from activity (`shared/js/matching/insights.js`, every page, just before `main.js`):** only with consent. Namo asks once (`Insights.askHTML()`, buttons `data-consent`); the answer is `S.learn` (undefined = not asked). With a yes it records rooms opened and seconds spent (`S.act.v`, by wrapping `open()` and the dialog's close event) and settled Rooms filters (`S.act.q`, from `browse.js` `render()`), and `profile()` combines them with likes/hearts, bookmarks, inquiries and passes into typical rent, walk, room type, favored features and what they skip. "what do I like?" shows `summaryHTML()` and offers `suggestions()`; "stop learning" sets `S.learn = false` and deletes `S.act`. It never reads anything outside DormNamo (browsers don't allow reading other sites' cookies or history, and Namo doesn't try).

**Maps and nearby places:** there are two providers, chosen automatically. With no `shared/js/app/config.js` keys (the current setup), the map is Leaflet + OpenStreetMap tiles and nearby places come from OpenStreetMap via Overpass. With keys, Google is used.
- Dorm coordinates come from `shared/js/data/pins.js` (`PINS`, set by hand in the pin tool, `pin/`), drafts in `localStorage` (`dn:pinDrafts`, shown only on that device), or `lat`/`lng` in `data.js`. `DNMaps.applyPins()` merges them at load, and pins win.
- `npm run nearby` (`tools/osm-snapshot.mjs`) saves OSM results per pinned dorm into `shared/js/data/nearby-snapshot.js`, which is used when the pin hasn't moved. Live Overpass is only a fallback, because the public servers are slow (~25 s) and often return 502/504.
- The listing dialog `#dlg` (also Compare and profiles) glides in and out: `details.js` wraps `D.showModal`/`D.close` once (adds `.closing`, waits for `dlgOut` in `details.css`, then really closes; Esc goes through the same path; a `showModal()` while closing finishes the close first), so always close it with `D.close()`/`dlg.close()`, never by removing the `open` attribute. The map mounts ~300 ms after opening so it doesn't stutter the entrance. `details.js` defines a global `open(id)`, which shadows `window.open`. To open a URL, create an `<a target=_blank>` and click it (`openLink` in maps.js). Never call it from an inline `onclick="open(…)"`: inline handlers resolve `open` to `document.open()`, which blanks the page; use a `data-` attribute and a listener.

- `shared/js/maps/nearby-core.js` holds pure logic: `CATEGORIES` (Places types, radius, color, icon), distance and time formatting, the summary text, and an opening-hours check.
  - It is a UMD file. The browser gets the `NearbyCore` global, while the worker and the tests `import` it as CommonJS, so keep it free of the DOM and of ES-module syntax.
- `shared/js/maps/maps.js` (`DNMaps`): `details.js` calls `DNMaps.section(h)` while building the dialog HTML and `DNMaps.mount(h)` after `showModal()`.
  - **One** `google.maps.Map` is created per page and its canvas is moved into each dialog, because every new Map is a billed load.
  - Nearby data is memoized per listing and kept in `sessionStorage` for 1 h.
  - Everything fails soft: no key, no coordinates or a worker error shows a message, and the dialog still works.
- `worker/nearby.mjs` is a Cloudflare Worker with `GET /nearby?lat&lng` (and `POST /namo`).
  - It makes one Places API (New) Nearby Search per category, with optional Routes API times, and keeps a TTL cache in `worker/cache.mjs` (KV or memory).
  - `createHandler({fetch, store, now})` injects dependencies, which is how `tests/worker.test.mjs` mocks Google.
- `tools/geocode.mjs` edits `data.js` line by line through `tools/geo-lib.mjs`. Each listing must stay on one line as a JSON object.
  - The `geo` field records the source (`places`, `geocode:<type>` or `manual`) and `geoAt` the date. Coordinates from Google are refreshed after 30 days (Google's caching terms). `manual` ones are never touched.

**Owner listings (`shared/js/listings/listings.js`, every page, right after `photos.js`):** places owners add (Rooms "Add your property" form or `my-listings/`) live in `localStorage` (`dormnamo:listings`, one record per place with `ref` (UUID v4, given on save; older records get one once at load), `uid`, the HOUSES fields, `facts`, `plan`, `cover` and `photos` as JPEG data URLs). ## Conventions

- Page titles read `DormNamo | <Page>` (a vertical bar, not a dash or dot).
- Escape any user- or data-derived string with `esc()` before putting it into the `innerHTML` strings that build most of the UI.
- Code is formatted with Prettier (`npx prettier --write --print-width 110` on `shared/`, the page folders, `tools/`, `tests/`, `worker/`). Never format `shared/js/data/data.js` (the geocode tool needs one listing per line) or the generated `shared/js/data/pins.js`, `shared/js/data/nearby-snapshot.js` and `shared/js/app/config.js` (a `--ignore-path` file did not stop Prettier from rewriting them, so restore them if touched). The HTML pages are formatted the same way (Prettier's default whitespace handling keeps inline spacing).
- Keep the existing `var`, function expressions and no transpile-only syntax. Do not add a framework or a build step. (The worker and the tools are modern ES modules, `.mjs`.)
- UI icons are line SVGs from `ico(name)` (`ICONS` in `utils.js`) and the logo is `logoHTML()`. Don't use emoji in navigation, buttons, cards or bot replies (Namo and the test bot write plain text; Namo's avatar is `ico("namo")`, bot accounts get `ico("bot")` via `avatarHTML`). Only the Messages emoji picker and what people type contain emoji. The look is minimalist: no grid/graph-paper backgrounds, no particle bursts, no bouncy or rotating motion. Brand/Discover styles live in `shared/css/base/brand.css`.
- Rooms hero motion lives in `home/hero-fx.js` + the end of `shared/css/components/hero.css`: stat scramble, scroll depth (`--hp`), and the intro. `index.html` adds `class="intro"` to `<html>` in the head (hidden until `HeroFX.play()` runs from `startSite()`, with an 8 s fallback). Keep new hero children compatible with the `.hero .wrap > *` intro animation.
- `base.css` pads every `<section>` by 48px. Only the page sections want that, so any other `<section>` (the dialog's `.nb`, the pin tool's main column, Leaflet's layer switcher) must reset `padding`.
- Speed metrics: never start the whole page or the hero `h1` (the Largest Contentful Paint element) fully transparent or animated. Browsers only count animated or opacity-0 content as painted on a later repaint. The body fade starts at `opacity: .01` for that reason. This took FCP/LCP on the Rooms page from ~1.1 s/2.4 s to ~0.15 s.
- Glides to the room list go through `FX.resultsTarget(finder)`. On phones it targets the results bar, because the filter panel fills the first screen there.
- Fonts load as variable ranges (`Figtree:wght@400..800`, `Bricolage+Grotesque:wght@600..800`). Keep every weight used in CSS inside those ranges.
- Walking routes: clicking a nearby place (pin or list name) calls `routeTo()` in `maps.js`. It draws a dashed straight line at once, then the real path from the free OSRM routers (FOSSGIS `routed-foot` first, the OSRM demo car profile as backup with walking time estimated at 4.8 km/h), with the result in the `#nbRoute` bar under the map. No bubble, because it covered the route. Routes are memoized and kept in `sessionStorage`; `routeToken` drops stale responses. Parsing (`routeUrl`/`parseRoute`/`routeLabel`) is in `nearby-core.js` with tests. The routers ask for fair use and the "Routes © FOSSGIS / OSRM" credit.
- "Find your room" styles live in `home/finder.css`. Every visible `<select>` (search bar, filter "Near", "Sort by", and the owner form's Room type/Near/Plan) uses the custom `Dropdown` (`shared/js/app/select.js`, ids listed at its end); a new select should be added there too. When code sets a select's value, call `Dropdown.sync(select)` (browse.js `ddSync`) or the styled button shows the old choice. Set the price filter only through `setPrice(v)`, which keeps `F.p`, the slider, its `--fill` and the label in step.
